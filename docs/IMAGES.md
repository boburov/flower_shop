# Flower images

Product imagery is central to this project. Images are served as **plain static files** — the
simplest, most reliable approach (permanent URLs, CDN-cacheable, no runtime dependency on a bot).

There are three supported sources, in order of recommendation.

---

## 1. Local placeholders (default, dev)

The repo ships with tasteful SVG placeholders in `public/images/flowers/`, generated by:

```bash
node scripts/generate-placeholders.mjs
```

Each product's `imageUrl` points at one of these (e.g. `/images/flowers/pink-peonies.svg`). The
site runs and looks finished with zero configuration. Replace them with real photography anytime.

---

## 2. VPS static hosting (recommended for production)

Host your real flower photos as static files on your VPS and point the app at them.

**On the VPS** (nginx example): put JPG/WebP files under a web root and serve them from a
subdomain, e.g. `https://img.yourflowershop.uz/flowers/pink-peonies.jpg`.

```nginx
server {
  server_name img.yourflowershop.uz;
  root /var/www/flower-images;
  location / {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
  }
}
```

**In the app**, set two env vars:

```bash
NEXT_PUBLIC_IMAGE_BASE_URL="https://img.yourflowershop.uz"
IMAGE_REMOTE_HOST="img.yourflowershop.uz"
```

Then store VPS-relative paths on products, e.g. `imageUrl = "flowers/pink-peonies.jpg"`.
`resolveImageUrl()` in `lib/config.ts` prefixes them with the base URL, and
`next.config.ts` allows the host for Next.js Image optimization. Root-relative paths
(`/images/...`) and absolute `https://` URLs are always used as-is, so you can mix sources.

> **Why static files, not the `getFile` proxy, for production?** Telegram's download URLs are
> temporary and rate-limited, and the bot becomes a single point of failure for every image
> request. Static files on your VPS (or object storage / a CDN) are permanent and cache-friendly.

---

## 3. Telegram-hosted images (optional)

If you'd rather keep the source photos in Telegram, there's a complete pipeline — but note the
constraints below, and prefer option 2 for production delivery.

### Import workflow

1. Put image files (`.jpg/.png/.webp`) in a folder, e.g. `./import-images/`.
2. Create a bot with [@BotFather](https://t.me/BotFather), get its **token**, send the bot a
   message, and find your **chat id** (e.g. via [@userinfobot](https://t.me/userinfobot)).
3. Run the import (token/chat id are **server-only secrets** — never commit them):

   ```bash
   TELEGRAM_BOT_TOKEN=123:abc TELEGRAM_CHAT_ID=456 npm run telegram:import -- ./import-images
   ```

4. This uploads each photo and writes `data/telegram-images.json` mapping filename → `file_id`.

### Displaying them

`file_id` is **not** a public URL. Reference an image through the protected proxy, which
resolves it server-side on each request and caches the result:

```
/api/images/<file_id>
```

Set a product's `imageUrl` to that path. The proxy (`app/api/images/[fileId]/route.ts`) uses the
bot token on the server only; it returns `501` if no token is configured, so nothing breaks when
Telegram isn't set up.

### Constraints (per Telegram's API)

- `file_id` values are not ordinary image URLs.
- `getFile` download links are **temporary** — always go back through the proxy; never cache the
  raw URL in a product record.
- The bot token must **never** be exposed to the browser or placed in a `NEXT_PUBLIC_` variable,
  and must never be committed to Git.

---

## Switching to object storage / CDN later

Because images are just URLs resolved by `resolveImageUrl()`, moving to S3 / Cloudflare R2 /
Vercel Blob is a config change: upload the files, set `NEXT_PUBLIC_IMAGE_BASE_URL` to the bucket/
CDN origin, add the host to `IMAGE_REMOTE_HOST`, and store the object paths on products. No
component changes required.
